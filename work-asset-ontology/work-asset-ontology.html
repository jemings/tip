SLSI Agent Desktop · 워크에셋 v1 · 온톨로지 · 2026-11

v1은 문서의 문법을 정했다. 이제 문서 사이의 문법이 필요하다

워크에셋 v1 표준 덕분에 업무 폴더의 파일 하나하나는 형식이 잘 갖춰졌다. 이제 다음 질문은 이것이다 — 파일이 수백 개로 늘어도, 필요한 순간에 맞는 파일이 쓰일까? 복사해 갈라진 폴더, 대체된 옛 판, 같은 것을 다르게 부른 이름, 한도까지 쌓인 기준은 파일 하나가 아니라 파일들 사이에서 생긴다. 이 자료는 v1 코드를 직접 실행해 그 장면들을 확인하고, 온톨로지가 v1을 바꾸지 않고 그 위에서 어떻게 도울 수 있는지 설명한다.

쉽게 말하면v1은 책 한 권의 판형과 표지 규칙을 정했다. 온톨로지는 그 책들로 도서관 목록을 만든다 — "이 책은 저 책의 개정판", "이 두 책은 같은 주제", "이 규정은 이 업무에 적용".

v1 = 문서의 문법네 파일, 필수 머리말, 형식 검사
온톨로지 = 문서 사이의 문법파일을 읽어 만드는 색인. 지워도 언제든 다시 만들 수 있다

02 — 이런 장면, 익숙하지 않나요?

공들여 쓴 문서가, 정작 필요할 때 쓰이지 않는다

"관련 자료가 없습니다"

지난달 팀이 함께 정리한 위클리 리포트 작성 절차가 폴더에 있다. 그런데 "주간 보고 규칙 알려 줘"라고 하자 아바타는 관련 자료가 없다며 일반적인 보고서 형식으로 쓴다.

복사한 다음 날부터 멈춘다

올해 업무를 시작하려고 작년 폴더를 통째로 복사했다. 그때부터 "필수 업무 기준을 사용할 수 없습니다"라며 실행이 멈춘다. 원본만 연결해 둔 동료의 아바타까지.

규칙이 빠진 줄 모른다

정책 파일에 project: A-프로젝트라고 적었는데 아바타 설정은 A 프로젝트다. 오류도 경고도 없이 정책 없이 일하고, 팀 규칙을 어긴 결과물은 리뷰에서야 발견된다.

누구의 잘못도 아니다문서를 쓴 사람도, v1 표준도 제 할 일을 했다. 문서 하나하나는 올바르다. 아직 없는 것은 문서와 문서 사이를 이어 주는 정보 — "이건 저것의 새 판", "이 말과 저 말은 같다", "이 값과 저 값은 같은 프로젝트" — 이다. 이 자료는 그 빈자리를 함께 채우자는 제안이다.

세 장면은 실제 v1 코드를 합성 파일로 실행해 얻은 결과(07장)를 일상의 말로 옮긴 것이다.

03 — 먼저 결론

세 문장으로

1. 자산이 잠드는 곳은 파일 안이 아니라 파일 사이다

형식 검사를 통과한 좋은 파일만 모여도, 필요한 순간에 쓰이지 못하는 잠든 자산이 생길 수 있다. 복사본, 옛 판, 다른 이름, 넘치는 기준은 파일 하나만 들여다봐서는 알 수 없다.

2. 자료가 쌓이면 v1만으로는 풀기 어려운 장면이 생긴다

v1에서 문서와 문서를 잇는 방법은 폴더 위치, 값이 글자 그대로 같은지, 겹치지 않는 식별자 — 이 세 가지뿐이다. v1 코드를 직접 실행해 보니 폴더 하나를 복사하자 원본 폴더를 쓰던 아바타까지 실행이 멈췄고, project 한 글자 차이로 필수 정책이 아무 경고 없이 빠졌다.

3. 온톨로지는 v1 위에 선다

v1 형식과 검사는 그대로 둔다. 그 위에서 관계를 기록하고 어긋남을 보인다. v1에 부탁하는 것은 선택 항목 다섯 개를 문서 형식에 적어 두는 것과 작은 수정 두 가지뿐이다.

그래서온톨로지는 v1을 대신하는 것이 아니라 v1 위에 얹는 것이다. v1이 이미 정해 둔 파일 유형·담당자(owner)·식별자 덕분에, 온톨로지를 더 적은 비용으로 더 정확하게 만들 수 있다.

04 — v1이 이미 마련한 것

온톨로지의 절반은 v1이 이미 만들어 두었다

v1이 정한 것온톨로지가 그대로 쓰는 방식
업무 폴더마다 workflow·stakeholders·policy·verify 네 파일한 폴더 = 한 업무. 폴더가 온톨로지의 기본 단위가 되고, 파일의 역할은 따로 추측할 필요가 없다
필수 owner담당 팀·사람을 용어로 쓰고, 정리할 거리를 "내가 담당한 것"부터 보여 주는 기준이 된다
필수 work_asset_id대체·갈래 관계를 적을 때 가리키는 고정된 이름. 파일을 옮기거나 이름을 바꿔도 관계가 유지된다
work_asset_kind · policy는 필수 기준무엇이 매번 지침에 들어가고 무엇을 검색해서 읽는지가 정해져 있다. 그래서 policy.md는 앞으로도 늘 적용하고, 요청에 따라 넣고 빼는 대상(조건부 기준)으로 만들지 않는다
카드의 pipeline.json v1 (Task·Role·단계)Task 제목은 업무 용어가 되고, 단계는 그 Task의 구성 요소(part-of)가 된다. 역할 설명은 어떤 기준을 넣을지 고를 때 요청과 비교하는 글로 쓴다
형식 검사, 비표준 제외형식이 깨진 파일이 온톨로지의 근거로 섞여 들어오지 않는다

그러니이 자료가 v1에서 아직 다루지 않는 장면을 짚는 것은 v1을 되돌리자는 뜻이 아니다. v1이 토대를 놓았기에 그 위의 층을 이야기할 수 있게 되었다. 이 자료는 그 층이 왜 필요한지를 함께 살펴보려는 것이다.

05 — '잠든 자산'이란

업무 문서가 실제로 쓰이려면 세 단계를 모두 통과해야 한다

이 자료에서 잠든 자산은 내용이 부족한 파일이 아니다. 누군가 공들여 쓴 좋은 문서가 폴더에 멀쩡히 있는데도, 아래 세 단계 중 하나를 넘지 못해 일에 쓰이지 못하는 상태를 말한다. 문서를 쓴 사람의 수고가 결과로 이어지지 못하는 것이다.

먼저 알아 둘 것 — 워크에셋 파일은 두 가지 방식으로 쓰인다. 참고자료는 에이전트가 필요할 때 검색해서 읽는다. 기준은 실행할 때마다 에이전트의 지침에 자동으로 들어간다(policy.md는 항상 기준). ①은 주로 참고자료의 문제, ③은 기준의 문제, ②는 둘 다의 문제다.

① 검색된다

필요할 때 에이전트가 그 파일을 찾아낼 수 있는가

예: 사용자는 "주간 보고"라고 묻는데 폴더에는 "위클리 리포트"라고 적혀 있다 → 검색 결과 0건

막히면: 자료가 있는데도 "관련 자료가 없습니다"라고 하고 일반 상식으로 일한다

→

② 믿을 수 있다

찾은 파일이 지금 유효한 판인가, 다른 규칙과 어긋나지 않는가

예: 작년 폴더를 복사해 올해 폴더를 만들었는데 둘 다 남아 있다 → 검색하면 두 판이 함께 나온다

막히면: 작년 규칙대로 일하거나, 둘 중 아무것이나 고른다

→

③ 실행에 반영된다

지켜야 할 규칙이 실제로 에이전트의 지침에 들어가는가

예: 상위 폴더를 연결했더니 기준이 48,000자를 넘었다. project 표기가 한 글자 달라 정책이 빠졌다

막히면: 실행이 아예 멈추거나, 규칙이 빠진 줄 모른 채 일한다

→

쓰이는 자산

세 단계를 모두 통과한 파일만 실제 일에 쓰인다

하나만 막혀도 0이다못 찾으면 없는 것과 같고, 찾았는데 옛 판이면 오히려 일을 틀리게 만들고, 맞는 판이어도 지침에 안 들어가면 지켜지지 않는다. 더하기가 아니라 곱하기다 — 쓸모 = 검색 × 신뢰 × 반영, 셋 중 하나가 0이면 전체가 0이다.

v1과의 관계v1 형식 검사를 통과하면 파일은 이 세 단계에 참가할 수 있게 된다. 하지만 통과 여부는 파일 하나가 아니라 다른 파일과의 관계로 정해진다 — 다른 이름으로 적힌 같은 내용인지(①), 다른 판보다 새것인지(②), 다른 기준과 함께 들어갈 자리가 있는지(③). 그래서 형식 검사만으로는 이 단계들을 지켜 줄 수 없다.

발표자 정리 세 단계는 계획의 세 증상 (a) 못 찾음 (b) 낡음·중복·충돌 (c) 기준 한도와 같다. 예시의 동작은 07장에서 v1 코드로 직접 확인한 것이다.

06 — v1이 문서를 잇는 방법

v1에서 문서와 문서를 잇는 방법은 세 가지뿐이다

① 폴더 위치

아바타에 연결한 폴더 아래에 있으면 그 아바타가 쓰는 자료가 된다(_within). 하위 폴더까지 모두 포함된다.

자료가 쌓이면: 넓게 연결하면 하위 폴더의 필수 기준이 전부 지침에 들어가 한도를 넘고, 좁게 연결하면 옆 폴더의 자료를 못 본다.

② 값이 글자 그대로 같은지

project·role_id가 아바타의 값과 글자 그대로 같아야 실행에 들어간다.

자료가 쌓이면: 손으로 적는 값이 늘수록 표기가 갈린다. 안 맞는 자산은 기록 없이 빠진다.

③ 겹치지 않는 식별자

work_asset_id는 저장소 전체에서 하나뿐이어야 한다. 두 파일이 같은 id를 쓰면 둘 다 충돌 상태가 된다.

자료가 쌓이면: 폴더를 복사하는 순간 id가 겹친다. 그런데 복사는 새 업무를 시작하는 가장 흔한 방법이다.

빠진 것"이 파일은 저 파일의 새 판이다", "이 폴더는 저 폴더에서 갈라져 나왔다", "이 말과 저 말은 같다", "이 기준은 이 업무에만 적용된다" — 문서 사이의 이런 관계를 적을 곳이 v1에는 없다.

출처: backend/desktop/work_assets_store.py(_within, _scan의 식별자 판정, snapshot의 범위 걸러내기), work_assets_format.py(v1 검사). main 7dd26fdc9을 읽어 확인.

07 — 추측이 아니라 실행 결과

v1 코드를 직접 실행해 사람들이 흔히 하는 일을 해 봤다

# main 7dd26fdc9 의 FolderStore 를 임시 폴더로 직접 불렀다. 합성 파일, 운영 데이터 아님.

# ① weekly/ (policy.md 는 필수 기준) 를 weekly-2027/ 로 통째로 복사
statuses: weekly/policy.md identity_conflict, weekly/workflow.md identity_conflict,
          weekly-2027/policy.md identity_conflict, weekly-2027/workflow.md identity_conflict
snapshot(["weekly"])       → RUN BLOCKED: 필수 업무 기준을 사용할 수 없습니다 … weekly/policy.md (identity_conflict)
snapshot(["weekly-2027"])  → RUN BLOCKED: … weekly-2027/policy.md (identity_conflict)

# ② 상위 폴더 report/ 연결, 하위 정책 셋(각 15,000자)
snapshot(["report"])       → RUN BLOCKED: Required criteria exceed the 48,000 character context budget; narrow the scope

# ③ policy.md 에 project: "A-프로젝트", 아바타의 project 는 "A 프로젝트"
project='A-프로젝트'  criteria: 1
project='A 프로젝트'  criteria: 0      ← 오류도 경고도 없다

# ④ 같은 폴더에 회의록-1105.md
회의록-1105.md  invalid_format  'Use workflow.md, stakeholders.md, policy.md or verify.md'

# ⑤ 첫 머리글이 "주간 보고 정책" 인 파일을 찾는다
matches("주간 보고") → ['weekly/policy.md']
matches("주간보고")  → []

재현 스크립트와 원인 분석은 이슈 #2444에 있다. ①의 복사본은 weekly 범위 밖인데도 원본 실행을 막는다 — 식별자 충돌을 연결 범위와 상관없이 저장소 전체에서 판정하기 때문이다.

08 — v1 다음에 남은 과제 다섯

각각은 작아 보이지만, 모두 '쌓일수록' 커진다

#사람이 흔히 하는 일v1에서 일어나는 일자료가 쌓이면
V1옛 폴더를 복사해서 새 업무를 시작원본·사본 모두 식별자 충돌, 원본만 쓰던 아바타도 실행 정지복사가 잦을수록 실행이 자주 멈춘다. 피하려고 id를 손으로 바꾸면 두 폴더가 어떤 관계인지 기록이 사라진다
V2상위 업무 폴더 하나를 연결하위 폴더의 필수 기준이 전부 지침에 들어가 48,000자 초과 → "범위를 좁혀라"넓히면 막히고 좁히면 못 본다. 업무가 늘수록 둘 중 하나를 고르게 된다
V3project를 손으로 적음표기가 한 글자 달라도 필수 정책이 경고 없이 빠짐값을 적는 사람이 늘수록 표기가 갈린다. 빠진 줄도 모른다
V4회의록·사례·메모를 폴더에 둠정해진 네 파일 이름이 아니면 검색·실행에서 빠지고 "확인 필요" 목록에 쌓임지식이 거대한 workflow.md 본문에 몰리거나 밖에 남는다
V5"주간보고", "위클리 리포트"로 찾음검색어의 모든 낱말이 글자 그대로 들어 있어야 찾는다. 파일 이름이 넷뿐이라 구별할 단서는 폴더 이름과 본문 첫 제목뿐폴더가 늘수록 내가 떠올리지 못할 이름으로 적힌 폴더가 늘어난다

공통점다섯 모두 파일 하나는 멀쩡하다. 문제는 복사본과 원본 사이(V1), 상위와 하위 사이(V2), 내가 적은 값과 아바타의 값 사이(V3), 표준과 비표준 사이(V4), 내가 쓴 말과 파일에 적힌 말 사이(V5)에 있다.

09 — 예상 질문

"v1에 필드를 더 넣으면 되지 않나요?"

일부는 된다 — 그래서 선택 필드 다섯 개를 제안한다. 하지만 필드에는 사람이 알고 적은 것만 담긴다. 자산이 잠드는 원인 대부분은 누구도 알아채지 못해 적지 않은 관계에 있다 — 그런 관계는 모든 파일을 함께 놓고 비교해야 찾을 수 있다.

문제파일 필드로 되나왜
새 판이 옛 판을 대체선언은 된다supersedes 필드. 다만 옛 파일에 "대체됨"을 표시하고 검색 결과에서 뒤로 미루는 일은 두 파일을 함께 보는 쪽이 해야 한다
복사해서 갈라짐일부derived_from을 적을 수 있다. 하지만 탐색기로 복사한 사람은 적지 않는다 — 탐지가 필요하고, 원본이 나중에 바뀌었는지 알아차리는 것도 파일 하나로는 할 수 없다
중복·충돌안 된다중복인 줄 알면서 만드는 사람은 없다. 모든 파일을 서로 비교해야 드러난다
다른 이름일부aliases로 알고 있는 다른 이름은 적을 수 있다. 그러나 사용자가 검색창에 칠 말을 미리 다 알 수는 없다 — 찾기에 실패한 말을 모아 확정하는 길이 따로 있어야 한다
넘치는 기준일부applies_to로 적용 대상을 적는다. 그 대상이 지금 요청과 관련 있는지 판단하는 일은 실행할 때 앱(서버)이 한다
시간이 지나 낡음일부review_by로 기한을 적는다. 기한이 지났는지 날짜를 확인해 알려 주는 일은 앱이 한다

그리고 필드를 필수로 만들면 안 되는 이유: v1은 형식 오류가 있는 필수 기준을 실행 전에 막는다. 관계 필드를 필수·엄격 검사로 넣으면 관계를 적다 낸 오타 하나가 실행 전체를 멈추게 된다. 그래서 다섯 키는 선택이고, 틀리면 그 키만 무시하고 화면에 알린다 — 파일은 빠지지 않는다.

10 — 자산이 잠들어 가는 고리

못 찾으면 복사하고, 복사하면 더 못 믿는다

  1. 못 찾는다다른 이름으로 적혀 있어 검색에 안 걸린다(V5)
  2. "없나 보다" — 복사해서 새로 만든다가장 가까운 폴더를 통째로 복사한다(V1)
  3. 비슷한 판이 늘어난다복사본, 옛 판, 조금씩 다른 정책이 섞인다
  4. 찾아도 어느 게 맞는지 모른다둘 다 걸리면 에이전트가 임의로 고르거나 사용자에게 묻는다
  5. 넓게 연결하면 막히고 좁히면 못 본다기준이 쌓여 48,000자를 넘거나(V2), 범위 값이 달라 경고 없이 빠진다(V3)
  6. 믿음이 줄고, 손이 덜 간다결과를 믿기 어려우니 문서를 고칠 동기도 줄고, 문서는 더 낡는다
  7. 다시 ①로 — 한 바퀴 돌 때마다 파일은 늘고 쓸 수 있는 것은 줄어든다

고리를 끊는 방법같은 것을 같다고 알아보기(용어·동의어 → ①), 복사와 대체를 기록하기(갈래·대체 → ②③), 지금 일에 맞는 기준만 넣기(조건부 기준 → ⑤). 셋 모두 파일들 사이의 관계를 적어 두는 곳이 있어야 가능하다.

발표자 정리 고리는 V1~V5와 계획의 세 증상을 인과로 이어 본 것이다. 에이전트가 자산을 저장·제안하는 흐름이 늘수록 ②가 빨라진다.

11 — 온톨로지란

온톨로지는 업무 문서용 도서관 목록이다

온톨로지는 업무에서 쓰는 말(용어)과, 그 말들·문서들 사이의 관계를 정리한 목록이다. 도서관은 같은 문제를 오래전에 겪고 통제 어휘(시소러스)로 풀었다 — 정해진 표제어, "→ 보라" 참조, 상위어·하위어, 관련어. 워크에셋 온톨로지는 그 위에 업무 문서에 필요한 관계를 더한 것이다.

도서관 목록워크에셋 온톨로지예
표제어용어 — 대표 이름 + 유형(업무·문서 유형·프로젝트·시스템·팀·사람)주간 보고 (문서 유형)
"→ 보라" (USE / UF)동의어위클리 리포트, WBR → 주간 보고
상위어·하위어 (BT / NT)is-a, part-of주간 보고 is-a 보고서
관련어 (RT)related-to주간 보고 ↔ 월간 실적
개정판 표시supersedes (파일 → 파일)올해 workflow.md가 작년 판을 대체
— v1 반영derived-from (파일 → 파일, 갈래)팀B 폴더가 공통 폴더를 복사해 시작, 둘 다 유효
—conflicts-with (파일 ↔ 파일)두 policy.md가 어긋남
—applies-to (파일 → 용어)보고서 공통 policy.md → 보고서

닫힌 어휘용어 유형 다섯, 관계 일곱뿐. 모델이 지어낸 유형·관계는 버린다. v1의 asset_type(workflow·policy…)은 파일의 역할이지 용어가 아니다 — "policy"라는 용어가 파일 수백 개에 걸려 있으면 아무것도 구별해 주지 못한다.

도서관 관계 이름은 ISO 25964-1(시소러스 표준). 오른쪽 열은 ADR 0034·0040의 결정. derived-from은 v1의 "복사해서 시작" 때문에 이번 검토에서 더했다.

12 — 한 장으로 보기

용어는 둥근 상자, 파일은 네모. 모든 선에는 근거가 달린다

  1. 주간 보고 is-a 보고서 — 주간 보고는 보고서의 한 종류이므로, 보고서에 적용되는 보고서공통/policy.md가 주간 보고에도 적용된다. 이렇게 이어받는 관계는 따로 저장하지 않고 찾을 때마다 계산한다.
  2. 팀B보고 derived-from 보고서공통 — 복사해서 시작한 갈래. 갈래 관계를 기록한 뒤 원본이 바뀌었기 때문에 "원본 바뀜"이 표시된다. 팀B가 그 변경을 따라갈지는 사람이 정한다.
  3. 올해 workflow.md supersedes 2025년 판 — 옛 판은 지우지 않고 "대체됨"으로 정리 후보에 올린다.
  4. 동의어 "위클리 리포트"도 근거가 있다 — 그것을 적은 파일(aliases)과 해시. 그 파일이 바뀌면 "근거 낡음"으로 표시된다.
13 — 다섯 과제에 대한 답

온톨로지가 맡는 것과 v1이 맡을 것을 나눈다

#온톨로지가 맡는 것v1이 맡을 것
V1 복사복사를 갈래(derived-from)라는 기록된 관계로. 저장할 때 비슷한 기존 폴더를 먼저 보이고, 탐색기 복사는 "폴더 복사본 의심"으로 잡는다. 원본이 바뀌면 "원본 바뀜"사본 때문에 원본 실행이 멈추지 않게(#2444)
V2 넓은 연결기준 예산 게이지(현황 1차), 상·하위 폴더 겹침 신호(2단계), workflow·verify 기준을 요청에 맞을 때만 싣는 조건부 적용(3단계). policy.md는 v1 뜻대로 늘 적용—
V3 범위 값범위 값을 용어로 정규화해 "범위 값 불일치 의심"(D20)을 현황 1차에 보인다. 값을 고치지는 않는다빠진 필수 기준을 실행 전에 알릴지(#2444)
V4 비표준색인하지 않는다(v1의 결정을 존중). 대신 현황에 비표준 문서 수를 사유별로 보인다그 수를 보고 v1 유형을 넓힐지
V5 다른 이름용어·동의어 우선 검색, 글자 2-gram 색인(띄어쓰기·조사 무관), 0건이면 가까운 용어, 찾기에 실패한 말을 [동의어로 추가]—

역할 구분실행이 멈추거나 기준이 빠지는 동작 자체는 v1 쪽에서 고칠 부분이다(#2444). 온톨로지는 그 위에서 관계를 기록하고 어긋난 곳을 보여 주는 층이다. 한쪽이 다른 쪽을 대신하지 않는다.

14 — 같은 질문, 두 갈래

"주간 보고 쓰는 규칙 알려 줘"

업무폴더/위클리리포트/workflow.md       ← 첫 머리글 "위클리 리포트 작성 절차"
업무폴더/위클리리포트-2025/workflow.md  ← 작년 판. 복사해서 만들었고 지우지 않았다
업무폴더/보고서공통/policy.md           ← 모든 보고서에 적용되는 공통 정책

v1만 있을 때

부분 문자열 검색
  1. 복사하던 순간 두 workflow.md가 같은 id → 식별자 충돌, 둘 다 검색에서 빠진다
  2. id를 손으로 바꿔 충돌을 풀었다고 하자. 에이전트가 search("주간 보고")
  3. 제목·경로·본문 어디에도 "주간"이 없다 → 0건, 자료마다 본문을 다 읽고 나서
  4. 운 좋게 "위클리"로 찾아도 두 판이 같이 나온다 — 어느 게 올해 것인지 파일만 봐서는 모른다
팀 규칙은 폴더에 멀쩡히 있는데 쓰이지 않거나, 작년 규칙으로 쓰인다.

v1 + 온톨로지

계획된 동작
  1. 복사본을 저장할 때 "비슷한 폴더가 있다 — 새 판인가, 갈래인가?"를 묻는다 → supersedes
  2. search("주간 보고")가 용어 주간 보고에 먼저 맞춘다 — 동의어 "위클리 리포트"
  3. 올해 판, 주간 보고가 보고서의 한 종류라서 함께 적용되는 공통 정책, "2025년 판은 대체됨" 표시를 한 번에 돌려준다
  4. 결과에 matched_by: term, 후보는 색인으로 좁혀 필요한 파일만 읽는다
올해 절차와 공통 정책으로 쓴다. 어떻게 찾았는지가 남는다.

덧붙여 — 동의어는 저절로 생기지 않는다. 머리말 aliases, 사용자가 켠 모델 보강(옵트인), 현황의 [동의어로 추가]에서만 온다. 그래서 새 업무 폴더를 만들 때 "다른 이름으로는 뭐라고 부르나요?"를 묻게 했다(15장).

15 — v1 위에서 더한 장치

쌓인 뒤 치우기보다 입구에서 묻고, 시간과 주인을 붙인다

저장할 때 비슷한 것을 먼저 보인다

save·propose가 새 파일을 만들면 같은 asset_type의 비슷한 기존 파일(같은 id를 쓰는 파일 포함)을 결과의 similar로 돌려준다. 에이전트는 "고칠까요, 새 판인가요, 갈래인가요?"를 묻는다.

이미 있는 저장 응답에 붙는 정보다. 검토 카드 큐가 아니고 아무것도 자동으로 고치지 않는다.

새 업무 폴더에는 다른 이름을 묻는다

온보딩과 저장 안내가 새 폴더를 만들 때 사용자에게 다른 이름을 묻고 aliases에 적는다. 검색이 0건이면 이름이 가까운 용어(near_terms)를 돌려준다.

모델 보강을 켜지 않은 사용자에게도 동의어 출발점이 생긴다. 사람이 답하므로 추측이 아니다.

검토 기한 review_by

대부분의 문서는 새 판 없이 조용히 낡는다. 기한이 지나면 정리 후보 "검토 기한 지남".

"대체됨"은 새 판이 있어야만 쓸 수 있다. 기한은 주인이 직접 정한 약속이라 판단이 분명하다.

정리 후보는 owner별로

v1에서 owner가 필수가 되었으니, 정리할 거리를 "내가 담당한 것"부터 보여 줄 수 있다.

공용 폴더는 담당자가 분명할 때 정리된다. 팀 집계를 새로 만들지 않고 순서만 바꾼다.

모두 개정 설계(ADR 0040)에 들어갔다. 표시만 하고 처리는 사람이 한다는 원칙은 그대로다.

16 — 예상되는 반론

"LLM이나 벡터 검색이 알아서 하지 않나요?"

"전부 프롬프트에 넣으면"

기준은 이미 전부 넣고 있고, 그래서 48,000자에 닿는다(V2). 길수록 비용이 들고 모델은 긴 맥락의 가운데를 놓치기 쉽다. 무엇보다 어느 판이 최신인지는 넣는다고 알 수 없다.

"벡터 검색이면 동의어도 찾잖아요"

뜻이 비슷한 것은 잘 찾는다. 하지만 비슷함과 유효함은 다르다 — 작년 판과 올해 판, 원본과 복사본은 서로 가장 비슷한 문서라 함께 위에 뜬다. 팀 약어·과제 코드명은 임베딩이 모르고, 왜 그 결과가 나왔는지 사람이 고칠 수 없다.

"폴더를 잘 나누면"

폴더는 분류 기준이 하나뿐이다. v1에서는 그 폴더 위치가 아바타가 볼 범위까지 정하기 때문에, 넓게 연결하면 한도를 넘고 좁게 연결하면 옆 폴더를 못 보는 양자택일이 된다(V2). 폴더 계층은 버리지 않고 온톨로지의 첫 재료로 쓴다.

"사람이 가끔 정리하면"

맞다, 처리는 사람이 한다. 문제는 어디를 봐야 하는지다. 수백 개 폴더를 하나씩 열어 비교하는 것은 현실적으로 어렵다. 온톨로지는 후보를 골라 보여 주기만 하고 지우거나 합치지 않는다.

요약LLM은 똑똑한 사서다. 하지만 목록 없는 서고에서는 똑똑한 사서도 책장을 처음부터 훑는다. 온톨로지는 사서를 대신하지 않고 목록을 쥐여 준다.

17 — "온톨로지도 결국 방치되지 않을까요?"

그렇게 되지 않도록 처음부터 정해 둔 다섯 가지

  1. 파일이 원본이다

    온톨로지는 지워도 파일에서 다시 만든다. 지금처럼 편집기로 파일만 고쳐도 온톨로지가 따라 바뀐다.

    없으면: 원본이 둘이 된다
  2. 어휘가 닫혀 있다

    용어 유형 5, 관계 7. 그 밖의 출력은 어디서 오든 버린다.

    없으면: 지어낸 이름이 쌓인다
  3. 모든 주장에 근거

    근거 = 파일 id와 그 시점의 해시. 근거 파일이 바뀌면 "낡음"으로 표시하고, 사라지면 확정에서 후보로 낮춘다.

    없으면: 맞는지 검증할 수 없다
  4. 표시만, 처리는 사람

    자동 보관·삭제·병합 없음. 항목마다 검토 카드를 띄우는 큐도 없음.

    없으면: 검토 카드가 또 쌓인다
  5. 모델은 옵트인

    모델 없이 만드는 기본 구조는 항상 동작한다. 모델 보강은 저장소별로 직접 켤 때만 쓰고, 파일 내용이 어디로 전송되는지 화면에 보여 준다.

    없으면: 업무 문서가 모르게 나간다

v1을 위해 하나 더선택 머리말이 틀려도 파일을 실행에서 빼지 않는다. 온톨로지 때문에 실행이 멈추는 경우는 하나도 늘지 않는다. 또 검색은 "이 아바타에 연결된 범위"와 "이번 실행이 시작할 때 고정한 판"에 근거한 관계만 본다 — 다른 아바타의 자료가 섞이지 않고, 실행 도중 파일이 바뀌어도 답이 흔들리지 않는다.

ADR 0034(파생 구조·닫힌 어휘·필수 근거·범위 질의), ADR 0035(모델 보강 옵트인), ADR 0040(v1 위의 범위·선택 필드).

19 — 계획도 같은 눈으로 점검했다

계획에서 빈틈 여덟 개를 찾아 보완했다

찾은 빈틈고친 방법
설계가 v1 표준보다 먼저 쓰여 자유 형식 문서를 전제했다ADR 0040: 자산은 v1 표준 파일, 단위는 업무 폴더. 모델 없이 만드는 기본 구조의 재료에 owner·project·pipeline.json Task를 더했다
v1에서 가장 흔한 "복사해서 시작"을 표현할 관계가 없었다(대체로 적으면 멀쩡한 원본이 낡음이 된다)관계 derived-from(갈래) 추가, 양 끝 해시로 "원본 바뀜"
3단계가 policy.md도 조건부로 만들 수 있었다 — v1의 "정책은 공통 규칙·필수 기준"과 모순policy.md는 조건부가 되지 않는다. 정책만으로 한도에 닿는 경우는 한계로 적었다
#2216이 남긴 "Task별 자산 선택"과 3단계가 같은 문제를 따로 풀려 했다. 실행은 Task를 모른다(#886)Task를 실행 키가 아니라 업무 용어로. 3단계 ADR이 두 문제를 한 규칙으로 푼다
동의어 이득이 옵트인 모델에 달려 출발점이 약했다새 폴더에 다른 이름 묻기, 0건이면 near_terms, [동의어로 추가] 옆에 그 뒤에 읽은 자료를 힌트로 표시
위생 장치가 모두 사후 표시였다저장 결과의 similar(입구 확인)
새 판 없이 시간이 지나 낡는 문서를 잡지 못했다review_by → "검토 기한 지남"
검증이 재현율만 봐서 "찾았는데 옛 판"을 못 잡았고, 질의와 코퍼스를 같은 손이 쓸 수 있었다v1 모양 코퍼스(복사본·상하위 정책·표기 갈린 값), 옛 판이 위에 오는 비율의 상한, 질의를 따로 쓰기, 단계별 관찰 항목

아직 남은 한계(미리 밝혀 둔다): 온톨로지는 v1 표준 파일만 본다 · 탐색기 복사는 입구 확인을 거치지 않는다 · 모델 보강을 안 켜면 충돌 신호가 없다 · 조건부 기준은 모르는 표현이면 빠진다(빠진 목록으로 보인다) · 모든 재현율·용량 수치는 합성 코퍼스 기준이다.

20 — v1과 함께 정할 것

함께 정하고 싶은 것은 작고, v1 자산이 얻는 것은 크다

v1과 함께 정하고 싶은 것

  • 선택 필드 다섯 개를 문서 형식에 올리기 — aliases, applies_to, supersedes, derived_from, review_by를 v1 문서·온보딩 안내에 선택 필드로 적기. 검사기는 바꾸지 않는다(지금도 모르는 키를 허용한다)
  • #2444의 수정 두 가지 — 복사본이 원본 실행을 멈추지 않게, 범위 값 불일치로 빠진 필수 기준이 보이게
  • Task별 자산 선택 후속 설계를 3단계 ADR과 한 결정으로
  • 현황의 비표준 문서 수를 보고 v1 유형을 넓힐지 판단하기

온톨로지로 v1이 얻는 것

  • "파일 하나하나는 맞는데 모아 놓으면 어수선한" 상태를 눈에 보이게 — 복사본, 옛 판, 겹친 정책, 갈린 범위 값
  • 폴더 이름·첫 머리글뿐이던 구분자에 용어와 동의어를 더해 v1 자산을 실제로 찾을 수 있게
  • 넓은 연결이 48,000자에 막히는 문제에 예산 게이지와 조건부 적용이라는 출구
  • v1 형식을 쓰는 사람이 많아질수록 더 잘 찾는 구조 — 쌓일수록 나빠지는 곡선을 뒤집는다

한 줄로v1은 바꾸지 않는다. v1이 문서마다 정한 문법 위에 문서들 사이의 문법을 하나 더 얹는다.

21 — 동료들에게

구현을 기다리지 않고 지금 할 수 있는 일

폴더 이름은 사람이 부르는 이름으로

v1에서 파일 이름은 넷뿐이라 폴더 이름과 첫 머리글이 유일한 구분자다. tmp2·새 폴더 대신 "주간보고", "검증-릴리스".

폴더를 복사하면 work_asset_id부터 바꾼다

안 바꾸면 원본을 쓰던 아바타까지 멈춘다(#2444가 고쳐질 때까지). 바꾼 뒤 derived_from: <원본 id> 또는 supersedes: <옛 id>를 적어 둔다.

project·role_id는 복사해서 붙인다

손으로 다시 치지 않는다. 한 글자만 달라도 필수 정책이 경고 없이 빠진다.

다른 이름을 aliases로

aliases: [위클리 리포트, WBR]. 지금은 검색에 안 쓰이지만 v1 검사를 통과하고, 1단계의 재료가 된다.

머리말 선택 필드의 효과는 계획(#2124~#2126)이 계획대로 들어온다는 가정 위의 이야기다. 오늘 앱이 읽는 필드는 v1 필수 필드와 project·role_id다.

정리

책이 잘 만들어져 있어도, 목록이 있어야 도서관이 된다

v1만 있으면

파일 하나하나는 맞지만, 복사본·옛 판·다른 이름·넘치는 기준이 쌓일수록 검색·신뢰·반영 세 단계에서 막히는 일이 늘어난다. 직접 실행해 보면 실행이 멈추거나 기준이 경고 없이 빠진다.

v1 + 온톨로지

v1의 파일 유형·담당자·식별자 위에 근거가 달린 관계가 쌓여, 자료가 늘수록 동의어와 관계도 는다. 원본은 그대로 파일, 모델은 초안만, 처리는 사람이 한다.

한 문장v1은 문서의 문법, 온톨로지는 문서 사이의 문법 — 둘이 함께 있어야 워크에셋이 쌓일수록 더 잘 쓰인다.

v1이 파일마다 형식을 정해 둔 덕분에 이 계획이 현실적인 크기가 되었다. 동료들이 공들여 쓴 문서가 필요한 순간에 제대로 쓰이도록, 그 위의 층도 함께 만들어 가면 좋겠다.
