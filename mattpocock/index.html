바이브 코딩이 아니라 진짜 엔지니어링을 하는 에이전트 스킬

02 — 왜 존재하나

에이전트가 망하는 네 가지 방식

저자는 이 스킬들을 "기능"이 아니라 "실패 모드에 대한 처방"으로 설계했다. 네 가지 실패와 각각의 처방이 곧 스킬 목록의 뼈대다.

1. 내가 원한 걸 안 만든다

"No-one knows exactly what they want" David Thomas & Andrew Hunt, The Pragmatic Programmer

사람과 에이전트 사이의 소통 격차. 처방은 착수 전 심문이다.

grill-me · grill-with-docs

2. 말이 너무 장황하다

"With a ubiquitous language, conversations among developers and expressions of the code are all derived from the same domain model." Eric Evans, Domain-Driven Design

용어를 모르니 한 단어로 될 걸 스무 단어로 쓴다. 처방은 공유 언어(CONTEXT.md)다.

domain-modeling

3. 코드가 동작하지 않는다

"The rate of feedback is your speed limit." David Thomas & Andrew Hunt, The Pragmatic Programmer

피드백 루프 없이 날아가는 중. 처방은 red → green 루프다.

tdd · diagnosing-bugs

4. 진흙 덩어리가 됐다

"The best modules are deep." John Ousterhout, A Philosophy of Software Design

에이전트는 코딩만 빨라진 게 아니라 엔트로피도 빨라진다. 처방은 깊은 모듈이다.

codebase-design · improve-codebase-architecture

공유 언어는 장황함을 줄이는 데서 그치지 않는다. 변수·함수·파일 이름이 같은 어휘로 붙고, 코드베이스 탐색이 쉬워지고, 에이전트가 생각에 쓰는 토큰도 줄어든다.

03 — 구조

누가 부를 수 있는가로 갈린다

25종은 한 축으로만 나뉜다. 내가 직접 쳐야만 열리는 것과 에이전트가 알아서도 집는 것. 전자는 흐름을 지휘하고, 후자는 재사용 가능한 규율을 담는다.

--- skills/productivity/grill-me/SKILL.md name: grill-me description: A relentless interview to sharpen a plan or design. disable-model-invocation: true # ← 슬래시 전용

이 한 줄은 에이전트가 보는 목록에서만 스킬을 빼낸다. 그래서 빠지는 쪽이 user-invoked 14종이고, 거기 남는 건 model-invoked 11종이다. 사람이 슬래시로 부를 수 있는 건 25종 전부다 — 사라진 14종도 이름을 치면 그대로 열린다. user-invoked 스킬은 model-invoked 를 부를 수 있지만, user-invoked 끼리는 서로 부르지 않는다.

04 — 설치

세 줄이면 끝난다

# 1. 설치 — 공식 마켓플레이스라 등록 절차가 없다 /plugin install mattpocock-skills # 2. 이미 떠 있는 세션이면 스킬 목록 갱신 /reload-plugins # 3. 저장소당 한 번 — 이슈 트래커·라벨·문서 배치를 기록 /mattpocock-skills:setup-matt-pocock-skills
# Codex 등 다른 에이전트, 또는 스킬을 직접 고쳐 쓰고 싶을 때 npx skills@latest add mattpocock/skills # 설치기에서 setup-matt-pocock-skills 를 반드시 같이 고른다

두 방식은 철학이 다르다. 플러그인은 구독(읽기 전용 묶음, 저자가 올리면 자동 갱신), skills.sh 는 포크(내 저장소에 파일로 들어와 마음대로 수정). 둘 다 깔면 스킬이 두 벌이 된다.

setup 이 정하는 것 — 셋

  • 이슈 트래커 — GitHub / GitLab / 로컬 마크다운 / 직접 서술
  • triage 라벨 — 표준 5종을 쓸지, 기존 어휘에 매핑할지
  • 도메인 문서 배치 — 기본은 단일 컨텍스트, 모노레포 신호가 있을 때만 멀티를 묻는다

setup 이 남기는 것

  • docs/agents/issue-tracker.md — 이슈 조작 명령 규약
  • docs/agents/triage-labels.md — 역할 → 실제 라벨 매핑표
  • docs/agents/domain.md — 탐색 전 읽을 문서와 그 규칙
  • CLAUDE.md(없으면 AGENTS.md)의 ## Agent skills 블록 — 위 셋으로 가는 포인터

모두 평범한 마크다운이다. 나중에 직접 고치면 되고, 트래커를 바꾸거나 처음부터 다시 할 때만 setup 을 다시 돌리면 된다.

05 — 메인 플로우

아이디어에서 배포까지, 한 줄기

grill-with-docs user

심문으로 아이디어를 깎는다. 작업 디렉터리가 있으면 무조건 여기서 시작 — 배운 것을 CONTEXT.md 와 ADR 로 남긴다.

대화로 안 풀리는 질문(상태 모델·비즈니스 로직·눈으로 봐야 할 UI)은 handoff → prototype → handoff 로 우회

to-spec → to-tickets user

여러 세션짜리 작업이면 대화를 스펙으로 굳히고, 서로의 선행 관계를 선언한 tracer-bullet 티켓으로 쪼갠다. 한 세션이면 이 단계를 건너뛴다.

implement user

티켓 하나에 세션 하나. 각 티켓이 자기 완결적이라 직전 컨텍스트는 버려도 된다.

tdd → code-review model

implement 가 내부에서 돌리는 두 규율. 슬라이스마다 red → green, 마지막에 두 축 리뷰를 거쳐 커밋한다.

온램프 — 여기서 합류한다

  • 쌓인 버그·요청 → triage. 단, 내가 만들지 않은 이슈만. to-tickets 가 뽑은 티켓은 이미 에이전트용이라 triage 를 돌리지 않는다.
  • 뭔가 깨졌다 → diagnosing-bugs
  • 한 세션에 안 들어가는 안개 같은 과제 → wayfinder. 결정 티켓의 지도를 만들어 하나씩 해소하고, 안개가 걷히면 만들지 않고 to-spec 으로 넘긴다.

컨텍스트 위생

grill-with-docs → to-spec → to-tickets 는 한 컨텍스트 안에서 끊지 않는다. 셋이 같은 사고 위에 쌓여야 한다. 한계는 모델이 또렷하게 추론하는 구간(smart zone, 최신 모델 기준 약 150k 토큰) — 그 전에 차면 무리하지 말고 단계 경계에서 /compact 한다.

06 — 정렬: grilling

정렬: 만들기 전에 심문당하기

저자가 가장 많이 쓰이는 스킬로 꼽는 것. 설계 트리의 모든 가지가 닫힐 때까지 질문을 던진다. 사실 확인은 에이전트 몫, 결정은 내 몫이라는 규칙이 이 스킬의 핵심이다.

같은 심문, 두 갈래

  • grill-me — 상태를 남기지 않는다. 저장소가 없는 곳(계획·글·설계 아이디어)에서 쓴다.
  • grill-with-docs — 같은 심문에 흔적이 남는다. 용어는 CONTEXT.md 용어집으로, 되돌리기 힘든 결정은 ADR 로. 저장소 안이면 항상 이쪽이 낫다.

grilling 은 이 심문 자체를 담은 model-invoked 기본 단위이고, triage·wayfinder·improve-codebase-architecture 도 내부에서 같은 기본 단위를 돌린다.

공유 언어가 만드는 차이

BEFORE

"코스의 섹션 안에 있는 레슨이 '실체화'될 때(즉 파일 시스템에 자리를 받을 때) 문제가 생긴다"

AFTER

"materialization cascade 에 문제가 있다"

저자의 실제 CONTEXT.md 예시. 이 한 줄 압축이 세션마다 되풀이해서 제 값을 한다.

곁가지로 붙는 것들

  • research — 1차 출처를 백그라운드로 조사해 출처를 인용한 마크다운을 남긴다
  • to-questionnaire — 막힌 답이 내 머리도 코드도 아닌 다른 사람 안에 있을 때, 그 사람에게 보낼 질문지를 만든다
  • wait-what — 방금 들은 말이 이해되지 않을 때. 빠진 맥락을 채워 평범한 말로 다시 설명한다
07 — 구현: tdd

구현: 슬라이스 하나씩

implement 자체는 다섯 줄짜리 껍데기다 — 스펙대로 만들고, 가능한 곳은 tdd 로, 타입체크와 단일 테스트는 자주·전체 스위트는 마지막에 한 번, 끝나면 code-review, 그리고 현재 브랜치에 커밋. 알맹이는 tdd 에 있다.

seam 을 먼저 합의한다

seam 은 내부를 들여다보지 않고 동작을 관찰하는 공개 경계다. 테스트는 seam 에만 놓는다. 합의되지 않은 seam 에는 테스트를 쓰지 않는다 — 모든 걸 테스트할 수 없으니, 테스트할 힘을 임계 경로와 복잡한 로직에 먼저 몰아주기 위한 규칙이다.

# 루프의 규칙 red before green # 실패하는 테스트 먼저, 통과할 만큼만 구현 one slice at a time # seam 하나, 테스트 하나, 최소 구현 하나 refactor ∉ loop # 리팩터링은 리뷰 단계의 일

안티패턴 셋

  • 구현 결합 — 내부 협력자를 mock 으로 막거나 DB 를 직접 조회해 검증한다. 증상: 동작은 그대로인데 리팩터링하면 테스트가 깨진다.
  • 동어반복 — expect(add(a, b)).toBe(a + b). 코드와 같은 방식으로 기대값을 다시 계산하니 구조상 항상 통과한다. 기대값은 독립된 출처(알려진 리터럴·손으로 푼 예제·스펙)에서 와야 한다.
  • 수평 분할 — 테스트를 몰아 쓰고 구현을 몰아 쓴다. 상상한 동작의 모양만 검증하게 된다. 수직 슬라이스로: 테스트 하나 → 구현 하나 → 반복.

인터페이스 모양이 의심스러우면

codebase-design 을 참조로 끌어온다. 모듈·인터페이스·깊이·seam·어댑터· 레버리지·지역성 어휘의 정본이며, 돌리는 세션이 아니라 읽는 참조다. 좋은 모듈은 깊다 — 작은 인터페이스 뒤에 많은 동작.

08 — 검증: code-review

검증: 두 축을 따로 본다

고정점(커밋·브랜치·태그·머지베이스)부터 HEAD 까지의 diff 를 두 축으로 본다. 두 축은 병렬 서브에이전트로 돌려 서로의 컨텍스트를 오염시키지 않는다.

Standards

이 저장소가 문서화한 코딩 규칙을 지켰나. 거기에 Fowler 냄새 기준선이 얹힌다.

Spec

원 이슈·스펙이 시킨 걸 충실히 구현했나. 커밋 메시지의 #123 을 따라가 트래커에서 원문을 가져온다.

Spec 축이 docs/agents/issue-tracker.md 를 읽는다. 파일이 없으면 스킬이 여기서 멈추고 setup 을 돌리라고 말한다.

냄새 기준선 — Refactoring 3장 12종 중 6종

냄새 처방
Mysterious Name이름을 바꾼다. 정직한 이름이 안 나오면 설계가 흐린 것이다
Duplicated Code공통 모양을 추출해 양쪽에서 호출한다
Feature Envy탐내는 데이터 쪽으로 메서드를 옮긴다
Data Clumps같이 다니는 필드를 한 타입으로 묶는다
Primitive Obsession도메인 개념에 자기 타입을 준다
Repeated Switches다형성으로 바꾸거나 두 곳이 공유하는 맵으로 바꾼다

나머지 여섯은 Shotgun Surgery · Divergent Change · Speculative Generality · Message Chains · Middle Man · Refused Bequest 다. 두 규칙이 이 기준선을 묶는다 — 저장소 문서가 이긴다(저장소가 허용한 걸 냄새로 잡지 않는다), 그리고 항상 판단의 문제다("Feature Envy 가능성"이지 위반 확정이 아니다). 툴링이 이미 강제하는 건 건너뛴다.

09 — 막혔을 때

막혔을 때 꺼내는 것들

model diagnosing-bugs

첫눈에 안 보이는 버그, 간헐적 flake, 두 정상 지점 사이에 스며든 회귀용. 이 스킬의 전부는 이 버그에서 실제로 red 가 뜨는 명령 하나를 확보하기 전에는 가설 세우기를 거부한다는 것이다.

피드백 루프 → 최소화 → 가설 → 계측 → 수정 → 회귀 테스트

회귀 테스트를 놓을 올바른 seam 이 없으면 그 사실 자체가 결론이다 — 얕은 seam 에 쓴 테스트는 거짓 안심만 준다. 그 결론은 improve-codebase-architecture 로 이어진다.

model wizard

사람만 할 수 있는 절차 — 인프라 프로비저닝, 자격증명·CI 시크릿 등록, 낯선 서드파티 대시보드 클릭, 일회성 마이그레이션. URL 을 열고 값을 받아 .env 와 GitHub secret 에 써넣는 대화형 bash 를 만들어준다.

에이전트가 직접 할 수 있는 일이면 이걸 쓰지 않는다.

model prototype

설계 질문 하나에 답하는 버릴 코드. 상태·로직 질문이면 공유 가능한 HTML 한 장, UI 질문이면 한 라우트에서 토글되는 여러 변형. 버린다는 건 코드를 쓰는 방식에 대한 제약이지 파기 약속이 아니다 — 결론은 실제 코드에 반영되고, 프로토타입 자체는 prototype/<name> 브랜치에 1차 출처로 남는다.

model resolving-merge-conflicts

진행 중인 merge·rebase 충돌을 헝크 단위로. 줄을 골라 붙이는 게 아니라 양쪽의 1차 출처까지 거슬러 의도로 해소하고 작업을 끝낸다. --abort 는 하지 않는다.

improve-codebase-architecture 는 기능 작업이 아니라 유지보수다. 며칠에 한 번 돌려 깊게 만들 후보를 리포트로 받고, 고른 하나를 그대로 심문으로 이어간다. 오래된 코드베이스에서 진짜 후보를 찾아주지만 진흙을 대신 치워주지는 않는다.

12 — 현장 팁

깔고 나서 부딪히는 것들

이미 떠 있는 세션엔 자동 반영되지 않는다

스킬은 세션 시작 시 로드된다. 다른 창에서는 /reload-plugins. 반대로 docs/agents/*.md 는 스킬이 실행될 때 그때 읽으므로 즉시 반영된다.

이름이 겹친다

Claude Code 내장 /code-review 와 별개다. 내장은 버그 사냥, 이쪽의 값어치는 Spec 축 — 이슈가 시킨 걸 했는지는 내장 리뷰가 보지 않는다.

implement 를 통째로 믿지 않는다

마지막 줄이 "현재 브랜치에 커밋"이다. 커밋 분류·제목 규칙·로컬 게이트가 있는 저장소라면 tdd 와 code-review 만 낱개로 끼워 넣는 게 낫다.

triage 는 라벨을 만들지 않는다

표준 5종(needs-triage·needs-info·ready-for-agent· ready-for-human·wontfix)이 트래커에 없으면 내가 먼저 gh label create 로 만들어 둬야 한다 — 스킬은 붙이기만 한다. 이미 라벨 자동화가 있는 저장소면 매핑표의 오른쪽 열을 기존 어휘로 바꾸는 쪽이 안전하다.

나만 쓰고 싶다면

설정을 팀 CLAUDE.md 대신 추적하지 않는 CLAUDE.local.md 에 넣고, 산출물 경로를 .git/info/exclude(클론 로컬)에 적는다. 공유 트리에 아무 변경도 남지 않는다.

뭘 써야 할지 모르겠으면

/mattpocock-skills:ask-matt 가 상황을 듣고 스킬과 경로를 골라준다. 25종을 다 외우고 있으라는 전제 자체가 없는 설계다.

# 기존 워크플로우가 굳어 있는 저장소에 끼워 넣는 법 — 낱개로 enter-issue 42 # 기존 진입 절차 그대로 ↓ 구현 중 tdd # seam 합의 → red → green, 슬라이스 단위 ↓ 마무리 직전 /mattpocock-skills:code-review # 고정점 = main. Spec 축이 이슈 #42 를 읽는다 ↓ close-issue # 기존 게이트·PR 플로우
