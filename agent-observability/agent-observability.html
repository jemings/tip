Agent Observability · OpenTelemetry · 2026-10

Agent가 왜 45초나 걸렸는지, 흔적을 남겨야 안다

Agent는 한 번의 요청 안에서 LLM·Tool·MCP·Retry·Handoff를 여러 번 오간다. 최종 답변만 보면 무엇을 했는지 알기 어렵다. Agent Observability는 그 실행 과정을 telemetry로 남겨 다시 펼쳐 보는 방법이다.

쉽게 말하면숙제를 한 번에 끝낸 게 아니라 여러 번 찾아보고 물어보고 다시 고쳤다면, 마지막 답만 봐서는 왜 오래 걸렸는지 모른다. 과정을 녹화해 둬야 어디서 막혔는지 찾을 수 있다.

오늘 가져갈 두 문장

1. Agent를 “답변 생성기”가 아니라 “실행 과정”으로 본다

한 번의 요청 안에서 Agent → LLM → Tool → MCP → LLM이 이어진다면, 각각을 연결해 하나의 Trace로 보는 것이 핵심이다.

2. OpenTelemetry는 그 흔적에 공통 이름을 붙이는 쪽이다

OpenTelemetry는 저장·대시보드 제품이 아니라 Telemetry를 표현하고 전달하는 표준화 계층이다. GenAI 쪽에도 Agent·Tool·MCP·모델 호출을 위한 Semantic Conventions가 만들어지고 있다.

그래서“모델이 느렸다”에서 끝나는 게 아니라 “Calendar tool이 30초, LLM은 1초씩 세 번”처럼 실행 경로를 설명할 수 있게 된다.

03 — Agent는 왜 블랙박스가 되나

같은 요청인데, 안쪽에서 여러 일이 일어난다

“회의 자료를 찾아서 요약하고, 결과를 문서에 저장해 줘.”

최종 답만 본다

black box
  1. “완료했습니다.”만 남는다
  2. 어떤 문서를 찾았는지 모른다
  3. 검색이 몇 번이었는지 모른다
  4. 느려졌다면 원인을 추측한다
원인 분석이 “Agent가 그랬다” 수준에서 멈춘다.

실행 흔적을 본다

trace
  1. invoke_agent 시작
  2. 검색 Tool 2회 → 문서 조회 1회
  3. LLM 3회 → 마지막에 저장 Tool
  4. 저장 API가 28초 걸린 것을 확인
문제의 위치와 반복 패턴을 바로 설명할 수 있다.

쉽게 말하면영수증만 보면 “얼마 냈는지”만 알 수 있다. 상세 내역을 보면 무엇을 몇 번 샀는지 안다.

Agent의 실행 경로에는 framework 내부에서 일어난 단계도 있고, 별도 서비스에 대한 원격 호출도 섞인다. 그래서 단일 로그 파일보다 연결된 Trace가 유리하다.

04 — 한 번의 실행을 펼쳐 보면

Agent Trace는 “한 줄짜리 로그”가 아니다

01invoke_agent · summarize-meeting-agent45.8s
02inference · gpt-5 · input 6.2k / output 4801.4s
03execute_tool · search_documents0.8s
04execute_tool · fetch_document3.1s
05inference · gpt-5 · requests another tool1.2s
06MCP · tools/call save_document38.2s
07inference · gpt-5 · final response1.0s

부모와 자식 관계가 중요하다

모든 단계가 같은 Trace ID 아래 연결되면, Agent가 전체 실행을 시작했고 그 안에 모델·Tool·MCP 호출이 포함됐다는 사실이 보인다.

시간이 길면 원인이 보인다

총 45.8초라도 어느 Span이 시간을 잡아먹는지 알 수 있다. Retry가 논리적으로 같은 작업에 포함됐다면 해당 작업의 Span이 그 시간을 덮을 수 있다.

핵심Agent Observability에서 중요한 것은 “로그를 많이 남긴다”가 아니라 한 요청의 실행 단계를 연결해서 본다는 것이다.

05 — OpenTelemetry는 무엇을 하나

제품이 아니라, 흔적의 공통 언어를 만든다

Application / Agent │ ├─ Span / Metric / Event │ ▼ OpenTelemetry SDK │ ▼ OTLP Export │ ▼ Collector │ ├─ Jaeger ├─ Grafana ├─ Datadog └─ 기타 Backend

OpenTelemetry가 정하는 것

Trace·Metric·Event를 어떻게 표현하고 서로 연결할지에 대한 공통 모델과 Semantic Conventions를 제공한다.

OpenTelemetry가 직접 하지 않는 것

“여기가 느리다”를 분석하는 저장소나 대시보드 제품 자체가 아니다. Backend는 별도로 선택한다.

GenAI가 붙으면서

일반 HTTP/DB Span만으로는 부족하니 모델 호출·Agent·Tool·MCP 같은 GenAI 작업에 이름과 Attribute를 붙이기 시작했다.

쉽게 말하면각 팀이 영수증 양식을 따로 만들면 비교가 어렵다. OpenTelemetry는 같은 칸 이름으로 기록하자는 약속에 가깝다.

06 — Agent를 Span으로 표현한다

Agent의 “행동 종류”가 Span 이름이 된다

invoke_agent

Agent 실행

같은 프로세스 안의 Agent invocation 또는 원격 Agent service 호출을 표현한다.

plan

계획·작업 분해

Agent가 먼저 전략을 세우거나 task decomposition을 수행하는 구간을 나타낸다.

execute_tool

Tool 실행

Agent가 실제 도구를 실행한 구간이다. 자체 Tool이든 MCP Tool이든 연결할 수 있다.

invoke_agent weather-forecast-agent INTERNAL
gen_ai.operation.nameinvoke_agent gen_ai.agent.nameweather-forecast-agent childchat → tools/call → chat

현재 Agent 관련 Semantic Conventions의 상태는 Development다. 즉 이름과 Attribute가 최종 고정된 단계는 아니다.

쉽게 말하면“심부름 전체”, “계획 세우기”, “실제로 전화하기”를 따로 표시해 두면 어느 단계에서 시간이 났는지 보인다.

07 — MCP까지 이어 붙이면

Agent → Tool → MCP Server도 한 Trace로 이어질 수 있다

invoke_agent weather-forecast-agent │ ├── chat {model} │ ├── tools/call get-weather ← MCP client span │ │ │ └── tools/call get-weather ← MCP server span │ └── chat {model}

왜 MCP를 따로 보나?

MCP는 JSON-RPC 기반이고, 하나의 Streamable HTTP 요청 안에서도 여러 MCP 메시지가 오갈 수 있다. 그래서 HTTP 요청 시간만 보는 것보다 MCP 수준의 Span이 더 많은 문맥을 준다.

중복 Span도 조심한다

MCP Tool 실행이 이미 상위 execute_tool로 정확히 추적되고 있다면, MCP instrumentation이 불필요한 별도 Span을 또 만들지 않고 기존 Span에 MCP Attribute를 붙이는 방식을 권장한다.

그래서“Tool이 느렸다”에서 멈추지 않고 “MCP client는 빨랐는데 server에서 30초가 걸렸다”까지 내려갈 수 있다.

OpenTelemetry의 MCP Semantic Conventions는 client/server Span과 session·operation Metric, context propagation을 별도로 정의하고 있다.

08 — Trace만으로 끝나지 않는다

한 번 자세히 보는 것과, 전체 추세를 보는 것은 다르다

TraceONE REQUEST

한 Agent 실행에서 어디를 거쳤는지, 어느 Span이 오래 걸렸는지 본다.

MetricSYSTEM TREND

평균 지연, Tool 호출 수, Token 사용량처럼 전체 추세를 본다.

EventPOINT IN TIME

상태 변화나 특정 시점의 사건을 기록한다. 오래 지속되는 작업 자체는 Span이 더 적합하다.

LogDETAIL

예외나 애플리케이션의 상세 진단 정보처럼 문맥이 많은 기록을 남긴다.

1.8sAgent p50
7.2평균 tool calls / request
32k평균 input tokens

쉽게 말하면Trace는 한 번의 CCTV, Metric은 한 달치 통계, Event는 “그 순간 무슨 일이 있었나”, Log는 “그때 남긴 자세한 메모”다.

09 — 그래서 어떤 질문에 답하나

Agent 운영에서 궁금한 질문이 바뀐다

느린가?

총 지연시간뿐 아니라 어느 Agent·Model·Tool·MCP가 병목인지 찾는다.

비싼가?

Input / Output Token 사용량, 모델별 호출 수, 요청당 Agent 실행량을 묶어 본다.

자꾸 실패하나?

Tool error, timeout, retry, Agent error를 Trace와 연결해 실패 지점을 본다.

Loop에 빠지나?

한 요청 안에 inference와 tool 호출이 비정상적으로 많이 반복되는 패턴을 찾는다.

어디서 품질이 깨지나?

어떤 Tool 결과 뒤에 재시도나 추가 계획이 집중되는지 실행 경로를 비교한다.

누가 무엇을 했나?

Agent 이름·버전·Tool 이름·MCP session 같은 문맥을 연결해 실행 주체를 구분한다.

핵심Observability가 좋아지면 “Agent가 이상하다”가 아니라 “이 경로에서 이 Tool이 8번 호출됐다”처럼 말할 수 있다.

10 — Prompt도 전부 기록할까

가장 유용한 데이터가, 가장 위험한 데이터일 수도 있다

기록하면 좋은 것

  • 모델 이름
  • Agent 이름 / 버전
  • Duration / Error
  • Input / Output token
  • Tool 이름
  • MCP method / session

주의해야 하는 것

  • Prompt 전체
  • Tool arguments
  • Tool result
  • 대화 내용
  • 사내 문서 / 개인정보
  • Secret / token

OpenTelemetry도 content capture를 별도로 본다

GenAI conventions는 input/output message 등의 content를 opt-in으로 다루고 있다. “무조건 다 수집”이 기본값인 설계가 아니다.

운영에서는 단계적으로

metadata 먼저 → 문제 재현이 필요할 때 제한된 content → 민감 데이터 마스킹·보존기간·접근권한을 따로 설계하는 식이 현실적이다.

중요: Observability는 디버깅 편의를 위해 사용자 데이터를 전부 복사하는 기능이 아니다. 무엇을 수집하지 않을지부터 정해야 한다.

쉽게 말하면블랙박스를 열었다고 차 안의 모든 대화를 영구 녹음할 필요는 없다. 필요한 계기판 정보만으로도 많은 문제를 찾을 수 있다.

11 — 좋은 Agent Trace의 조건

많이 남기는 것보다, 연결이 잘 되어야 한다

① 한 요청이 하나의 이야기로 이어진다

invoke_agent 아래에 model·tool·MCP 작업이 적절한 parent/child 관계로 연결되어야 한다.

② 이름과 Attribute가 비교 가능하다

“검색 호출”을 팀마다 제멋대로 이름 붙이면 집계가 어렵다. Semantic Conventions가 필요한 이유다.

③ 고카디널리티 데이터는 조심한다

URL 전체나 자유 텍스트처럼 값이 너무 다양하면 Span name이나 Metric label로 쓰기 곤란하다. 안정적인 식별자는 속성으로 남기는 편이 낫다.

④ 실패와 재시도도 같은 흐름에서 본다

자동 retry가 논리적으로 같은 작업이라면, “재시도된 요청 3개”보다 “한 작업이 3번 시도됐다”는 사실이 더 중요할 수 있다.

한마디로Agent Trace는 길게 쌓인 로그 더미가 아니라, 사건을 다시 재생할 수 있는 실행 지도여야 한다.

12 — LLM Observability와 Agent Observability

LLM 호출을 보는 것에서, 실행 주체를 보는 것으로

관심 대상모델 호출 1회하나의 목표를 수행한 전체 실행
주요 단위inferenceinvoke_agent · plan · execute_tool
질문어떤 모델이 얼마나 느렸나?왜 이 Agent가 이 Tool을 이 순서로 여러 번 불렀나?
외부 경계모델 APITool · MCP · 다른 Agent · Workflow

중요둘 중 하나를 버리는 게 아니다. LLM Trace는 Agent Trace 안의 한 조각이 되고, Agent가 커질수록 그 바깥의 실행 흐름이 더 중요해진다.

그래도 지금 보는 이유

Agent framework와 MCP가 늘어날수록 각 제품이 서로 다른 이름으로 telemetry를 만들면 운영 데이터가 갈라진다. 공통 Semantic Conventions의 방향 자체가 중요한 이유다.

그래서 도입할 때

“표준이 완성됐으니 그대로 붙인다”보다 표준 명칭을 최대한 따르고, 현재 버전을 명시하고, 변경 가능성을 감안해 instrument를 분리하는 방식이 안전하다.

쉽게 말하면도로 표지판은 생기고 있지만 아직 최종판은 아니다. 그래도 모두가 같은 방향으로 표지판을 세우기 시작했다는 건 중요한 흐름이다.

정리

Agent를 잘 보려면, Agent가 걸어온 길을 기록해야 한다

Agent Observability의 핵심은 실행 경로다

invoke_agent → inference → execute_tool → MCP → inference처럼 한 요청의 흐름을 연결해서 본다.

OpenTelemetry는 그 연결을 표준화하는 축이다

Trace·Metric·Event·Log를 쓰고, GenAI/Agent/MCP에 공통 이름과 Attribute를 붙이려는 방향으로 발전하고 있다.

이번 발표의 한 문장 “LLM이 무슨 답을 했는지”만 보는 Observability에서, “Agent가 목표를 달성하려고 무엇을 했는지”를 다시 재생하는 Observability로 넘어가고 있다.

다음 단계에서 실제 시스템에 적용한다면, 가장 먼저 Agent span → model span → tool span → MCP span의 최소 Trace 하나를 만드는 것부터 시작하면 된다.
