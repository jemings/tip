웹페이지가 Agent에게 자기 기능을 Tool로 제공한다

WebMCP는 웹 애플리케이션이 브라우저의 Agent에게 구조화된 Tool을 노출하도록 만드는 제안형 Web API다. Agent가 버튼을 찾아 클릭하는 대신, 페이지가 “무엇을 할 수 있는지”를 직접 선언한다.

DraftCommunity Group Report
Chrome 149Origin Trial
2 APIsImperative + Declarative
Toolscurrent core abstraction

기준일: 2026년 9월 30일. 현재 WebMCP 문서는 Web Machine Learning Community Group의 Draft Community Group Report(2026-09-28)이며, Chrome에서는 Origin Trial/Early Preview 형태로 실험 중이다.

02 — 왜 필요한가

기존 Browser Agent는 “UI를 보고 맞혀서 조작”한다

스크린샷 / DOM / 접근성 정보

Agent가 현재 화면을 관찰하고 버튼·입력창·상태를 스스로 해석해야 한다.

추론 → Click / Type / Scroll

“이 버튼이 장바구니인가?”처럼 의미를 추론한 뒤 좌표나 요소를 조작한다.

다음 상태를 다시 관찰

한 번의 클릭만으로 끝나지 않는 작업은 매 단계마다 화면을 다시 읽어야 한다.

변경에 취약

레이아웃·텍스트·메뉴 구조가 바뀌면 기존 자동화가 깨질 수 있다.

WebMCP의 방향: “Agent가 UI를 이해한다”에서 “Web App이 Agent용 capability interface를 제공한다”로 역할을 한 단계 바꾼다.

Chrome은 WebMCP의 목적을 구조화된 Tool을 제공해 Agent의 actuation을 더 빠르고 정확하게 만드는 것으로 설명한다.

03 — 한 장으로 이해하기

Web App은 Tool Producer, Browser Agent는 Tool Consumer

WEB APP │ ├─ JavaScript / HTML │ ▼ document.modelContext │ ├─ registerTool(...) ├─ getTools(...) └─ executeTool(...) │ ▼ BROWSER AGENT ├─ tool discovery ├─ structured arguments └─ tool invocation

Web App

이미 존재하는 client/backend 로직을 Agent가 호출할 수 있는 structured capability로 노출한다.

Browser

페이지가 등록한 Tool을 Agent에 연결하는 실행 계층이 된다.

Agent

LLM + rules + memory + tools를 바탕으로 어떤 Tool을 언제 사용할지 결정한다.

현재 spec은 document.modelContext 아래 registerTool(), getTools(), executeTool() API를 정의한다. 페이지 내부 JavaScript Agent도 Tool discovery/execute를 사용할 수 있고, 브라우저가 제공하는 Agent는 별도의 내부 메커니즘을 사용한다.

04 — MCP와 무엇이 다른가

이름은 비슷하지만, 연결 지점이 다르다

MCPWebMCPACP / A2A
연결 대상Agent ↔ 외부 Tool / DataWeb App ↔ Browser AgentAgent ↔ Editor / Agent ↔ Agent
주요 위치서버 / 애플리케이션브라우저의 Web App클라이언트 / 네트워크
현재 핵심Tools · Resources · Prompts 등Structured ToolsSession / Message / Task
형태ProtocolWeb APIProtocol
한 줄 요약: MCP를 “외부 capability 연결”이라고 보면, WebMCP는 “웹페이지 자체를 Agent-ready capability로 만드는 방법”에 가깝다.

WebMCP는 MCP의 browser transport를 정의하는 표준이 아니다. WebMCP가 정의하는 것은 웹페이지의 Tool 노출을 위한 Web API이며, Chrome 문서도 MCP와 WebMCP를 서로 다른 문제를 해결하는 기술로 비교한다.

05 — Imperative API

복잡한 페이지 로직은 JavaScript 함수 그대로 Tool로

// cartStore.add(...)는 기존 application logic document.modelContext.registerTool({ name: "add_to_cart", description: "Add a product to the cart", inputSchema: { type: "object", properties: { productId: { type: "string" }, quantity: { type: "integer", minimum: 1 } }, required: ["productId", "quantity"] }, execute: async ({ productId, quantity }) => cartStore.add(productId, quantity) });

name

Tool의 고유 식별자. Agent의 선택 대상이 된다.

description

Agent가 “언제 이 Tool을 써야 하는지” 이해하는 핵심 의미 정보다.

inputSchema

자유로운 텍스트 대신 구조화된 인자를 받도록 만든다.

execute

실제 페이지 상태 변경 또는 조회를 수행하는 application logic.

설계 포인트: 등록 시점에 상태를 캡처하기보다 실행 시점의 최신 application state를 읽는 쪽이 안전하다. Tool 정의는 의미 계약이고, 실제 상태는 execute가 결정한다.
06 — Declarative API

기존 HTML form도 Tool이 될 수 있다

<form toolname="search_flights" tooldescription="Search available flights" action="/search" method="get"> <input name="from" /> <input name="to" /> <input name="date" type="date" /> </form>

왜 필요한가?

웹의 많은 기능은 복잡한 JS 함수가 아니라 이미 semantic HTML form으로 구현되어 있다.

장점

기존 form을 크게 재작성하지 않고 Tool name, description, parameter semantics를 추가할 수 있다.

방향

“Agent 전용 코드”를 새로 만드는 것보다 기존 Web platform semantics를 재사용하는 접근이다.

toolnametooldescriptionform fields = argumentssemantic HTML

Chrome의 Declarative API 문서는 표준 HTML form에 Tool 이름·설명을 annotations로 추가해 browser가 Agent용 structured representation으로 번역하는 방식을 설명한다.

07 — 실행 모델

핵심은 “UI 자동화”가 아니라 “capability invocation”이다

1. Tool discovery

Agent가 현재 페이지에서 사용할 수 있는 Tool을 안다.

2. Semantic selection

Tool name / description / schema를 보고 목적에 맞는 기능을 고른다.

3. Structured invocation

productId, date, quantity처럼 명시된 인자를 넣어 Tool을 호출한다.

4. Application logic

페이지가 이미 가지고 있는 로직이 인증·상태·API 호출·화면 갱신을 수행한다.

중요한 관점: WebMCP는 Agent에게 “더 많은 권한”을 자동으로 주는 기술이 아니라, 기존 웹 애플리케이션의 capability를 더 명확한 interface로 노출하는 기술이다.
08 — 보안

Tool은 기능이 아니라 권한의 표면이다

Attack Malicious manifest

Tool name, description, parameters 등에 Agent의 행동을 유도하는 악성 지시가 숨어 있을 수 있다.

Attack Contaminated output

신뢰 가능한 사이트라도 댓글·사용자 입력·외부 데이터에 악성 지시가 섞여 Agent의 다음 행동에 영향을 줄 수 있다.

Hint readOnly

상태를 바꾸지 않는 Tool은 read-only annotation으로 표시해 불필요한 확인을 줄인다.

Hint consequential

결제·예약·삭제·송금처럼 영향이 큰 작업은 consequential hint 등을 사용해 사용자 확인을 유도한다.

설계 원칙: description과 실제 side effect가 일치해야 하고, 민감하거나 되돌릴 수 없는 작업은 명시적인 확인 경계를 둔다. “Tool을 등록할 수 있다”와 “Agent에게 자유롭게 실행시켜도 된다”는 같은 말이 아니다.

Chrome의 WebMCP security guidance는 indirect prompt injection과 Tool metadata/output을 통한 공격면을 별도로 다룬다. WebMCP spec에도 Security & Privacy Considerations가 포함되어 있다.

10 — 왜 주목할 만한가

웹이 “Agent-compatible UI”에서 “Agent-native interface”로 갈 수 있다

Before

Agent가 화면을 해석한다. UI가 사람에게 친절해야 하고, Agent는 그 UI를 다시 추론한다.

With WebMCP

Web App이 capability를 구조화해 제공한다. Agent는 “무엇을 할 수 있는가”를 직접 본다.

Reliability

레이아웃과 버튼 위치에 덜 의존한다.

Efficiency

불필요한 screenshot → click → observe loop를 줄일 수 있다.

Personalization

사이트의 실제 session/auth/state를 활용하면서 structured action을 수행할 수 있다.

이는 WebMCP가 “브라우저를 위한 또 하나의 자동화 API”라는 것보다, 웹 애플리케이션이 Agent에게 자신의 capability를 설명하는 새로운 interface layer라는 관점이 중요한 이유다.

11 — 웹 개발자 관점

Agent가 생기면 제품 설계 질문도 하나 늘어난다

UX

사람뿐 아니라 Agent도 이해하기 쉬운 의미와 상태를 제공하는가?

Capability

우리 서비스에서 Agent가 직접 호출할 가치가 큰 작업은 무엇인가?

Schema

Tool 이름·description·input schema가 의도를 충분히 표현하는가?

Security

읽기 / 변경 / 파괴적 작업을 어디에서 나눌 것인가?

질문을 이렇게 바꿔볼 수 있다. “사용자가 이 기능을 클릭해서 수행한다” ↓ “Agent가 이 기능을 Tool로 호출한다면 어떤 name / description / schema / confirmation이 필요한가?”

Chrome best practices도 Tool strategy → semantic language → schema/input → reliable tool → test/debug 순서로 설계를 권장한다.

12 — Agent ecosystem

지금까지 나온 기술을 “Agent가 무엇과 연결되는가?”로 보면

MCP

Agent ↔ External Capability
서버·데이터·도구 연결.

ACP

Agent ↔ Editor / Client
Agent를 다른 클라이언트가 제어·통합.

WebMCP

Web App ↔ Browser Agent
웹페이지가 자신의 기능을 Tool로 노출.

A2A

Agent ↔ Agent
서로 다른 Agent의 협업과 작업 위임.

주의: 이 그림은 “하나의 표준으로 통합된다”는 의미가 아니라, 현재 각 기술이 해결하려는 연결 경계를 비교하기 위한 개념도다.
13 — 도입 판단

“WebMCP를 붙일까?”보다 먼저 볼 세 가지

① 반복되는 중요한 사용자 작업

검색·예약·주문·신청·진단처럼 Agent가 대신 수행할 가치가 명확한가?

② 기존 application logic 재사용

새 자동화 코드를 만드는 것이 아니라, 이미 안정적인 business logic을 Tool로 연결할 수 있는가?

③ side effect와 trust boundary

읽기와 변경 작업을 어떻게 구분하고, 어디에서 사용자 확인을 요구할 것인가?

초기 도입에 잘 맞는 예: 검색 / 조회 / 필터 / 진단 / 계산처럼 비교적 명확한 read-oriented capability부터 시작하고, 결제·삭제·권한 변경 같은 consequential action은 별도 검토한다.
14 — Takeaways

오늘 기억할 것은 네 문장으로 충분하다

1. WebMCP = Browser-native capability interface

웹페이지가 Agent에게 structured tools를 제공하는 Web API.

2. UI 조작보다 capability 호출에 가깝다

Agent가 버튼의 의미를 추측하는 대신 사이트가 기능과 schema를 직접 제공한다.

3. MCP와 이름만 비슷하다

MCP의 브라우저 transport가 아니라, Web App ↔ Browser Agent를 위한 별도의 Web API다.

4. 아직은 early stage다

Draft spec + Chrome Origin Trial/Early Preview이므로 browser support·semantics·security가 계속 변할 수 있다.

한 문장: “웹이 사람에게 클릭 방법을 보여주는 것에서, Agent에게 자신이 할 수 있는 일을 API처럼 설명하는 것으로 진화하는 실험이다.”AI Agent Study summary · 2026-09-30
